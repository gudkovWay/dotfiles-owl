# Ponytail — минимальное полное решение

## HARD GATE

Упростить способ решения, не пользовательскую цель. Сохранить каждый критерий приёмки, validation, security, accessibility и защиту от потери данных. Правила владельца, native verification и Worktrunk определяют полномочия и исполнение; этот навык не добавляет агентов, gates или новые разрешения.

## Перед изменением

1. Прочитать задачу и затрагиваемый код. Назвать наблюдаемый результат и границы изменения.
2. Найти callers, tests, fixtures, config и exports, которые изменение обязано охватить. Для symbol references использовать LSP, когда сервер доступен; отсутствие сервера назвать, не угадывать callers.
3. Выбрать первый полностью подходящий вариант: существующий паттерн репозитория → стандартная платформа → уже установленная зависимость → минимальная новая реализация. Проектный компонент важнее постороннего «более нативного» виджета.
4. Зафиксировать одной строкой существенное решение и причину. Обычный технический выбор сделать самостоятельно; неизвестность, меняющая продуктовый результат, не подменять удобным допущением.

## Во время реализации

- Исправлять корень дефекта один раз в правильном владельце состояния/логики, а не добавлять специальный путь для симптома.
- Не добавлять wrapper, option, config, watcher, cache или abstraction «на будущее». Сохранить слои и соглашения репозитория.
- Меньше понятного кода — лучше; хитрая однострочность не проще. Перемещение кода сохраняет errors/validation и все callers.
- Не добавлять зависимость ради нескольких строк. Реальная новая зависимость требует основания и действующих полномочий.
- Не урезать vague request до «ядра» молча. Сначала получить доступные факты; полнота определяется пользовательским запросом, не размером diff.
- Не маскировать незавершённый критерий комментарием shortcut, TODO, mock, no-op или ослабленным assertion.
- Комментарий нужен для неочевидного ограничения/причины, а не пересказа операции.

## Проверка и результат

Использовать `skill://repository-testing` для native regressions и полного затронутого typecheck. Debugging, TDD и receiving-code-review — адресные методы; они не запускают второй процесс разработки.

Изменённый UI/runtime упражнять на разрешённой owned поверхности. Source review/self-check не заменяет tests, кадр или driving. Resource failure не разрешает автоматический повтор.

В результате указать конкретное изменение, реально выполненные проверки и оставшийся риск/непроверенное. Не обещать «готово» при обязательном pending/blocked критерии. Не добавлять отдельный финальный ритуал, если эти данные уже есть в отчёте.

## Failure modes

- Маленький diff, но пропущен caller/критерий → восстановить scope и закончить его, не объявлять «MVP».
- Новый wrapper/watch/state без наблюдаемой причины → использовать существующего владельца или удалить избыточность.
- Короткое решение ломает ошибки/границы → выбрать чуть более длинное корректное, добавить native regression.
- Static check выдан за runtime → вернуть честный статус и выполнить разрешённый сценарий либо назвать точный prerequisite.
