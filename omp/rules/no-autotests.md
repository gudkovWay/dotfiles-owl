# Тесты и typecheck: штатный стек репозитория, релевантный безопасный запуск

Действует для main, сабагентов и воркеров во всех репозиториях. Имя
`no-autotests` сохранено для существующих ссылок; это не запрет писать
тесты, запускать релевантные штатные тесты или typecheck.

1. **Написание и обновление — часть изменения поведения.** Для новой фичи
   добавлять релевантные поведенческие тесты; для багфикса — регрессионный кейс;
   при изменении существующей фичи обновлять затронутые тесты и фикстуры.
   Отдельная просьба «напиши тест» не нужна. Не плодить тесты ради количества:
   проверять наблюдаемое поведение, границы, ошибки и переходы состояния.
   Если тесты неприменимы или в репе нет настроенного стека — назвать причину,
   не устанавливать новый раннер и не создавать параллельную инфраструктуру.
2. **Способ тестирования определяется репой, не глобальным allowlist.**
   Перед выбором тестов/команды прочитать `skill://repository-testing`.
   Источник истины — manifest/task scripts, конфиги, существующие тесты и CI
   именно целевого worktree. Vitest/Playwright не обязательны для других реп.
   Использовать установленный штатный раннер с его окружением и setup.
3. **Автоматически разрешён конечный точечный прогон** новых/изменённых и
   непосредственно затронутых тестов после изменения поведения или при работе
   над тестами. Не требуется отдельный апрув на каждый такой прогон.
   В расследовании/ревью без правки не начинать запуск самовольно.
   Запрошенный пользователем запрет или более узкий объём имеет приоритет.
   В батче воркеры пишут тесты, но не запускают: main прогоняет общий
   релевантный набор после интеграции, последовательно и под ресурсной защитой.
   **Локальный typecheck — обязательная часть реализации**, если изменены
   типизируемый код, тесты или конфигурация, влияющая на типы, и в репозитории
   настроена штатная проверка. Первый запуск и повторы после исправления
   ошибок типов не требуют отдельного вопроса. Агент сам выбирает затронутые
   проекты по manifest/CI и проверяет их целиком с родным tsconfig, командой
   и критерием CI: проверка всего приложения не считается расширением scope.
   Общий код может требовать нескольких или всех CI-проектов; их число
   само по себе не создаёт approval gate. Нельзя заменять проектный typecheck
   проверкой отдельных файлов без его tsconfig или исключать из него тесты.
   Несвязанные проекты и широкий прогон «на всякий случай» не разрешены.
   Если штатной проверки нет, назвать этот факт, не устанавливать новый стек.
   В батче typecheck выполняет main после интеграции, не дочерние агенты.
4. **Запуск требует `rule://heavy-jobs-resource-guard`.** Один worker/serial
   режим там, где раннер это поддерживает; ограниченная выбранная группа
   файлов/кейсов/вариантов; без автоматических retries внутри раннера.
   Повтор после исправления причины по пункту 7 — не такой retry.
   Нельзя обходить caps другим процессом, агентом, внешним контейнером
   или браузерным daemon.
   Недоступна защита или нельзя ограничить прогон — `unverified` и блокер.
5. **Полный suite, coverage, watch/UI/debug, stress/benchmark и нагрузочные
   генераторы не входят в автоматическое разрешение.** Нужна явная просьба
   на соответствующий режим; она не отменяет caps, serial execution внутри
   выбранного test runner, запрет видимых окон и безопасность окружения.
   Независимые уже разрешённые jobs разных сессий/агентов могут выполняться
   параллельно только через общий бюджет `rule://heavy-jobs-resource-guard`.
   Один writable environment не менять параллельно; использовать штатный
   environment key/lock, без общих writable generated/dependency каталогов.
   Для ограниченного исправления разрешена необходимая подготовка по уже
   проверенному профилю: установка неизменённых lockfile-зависимостей с
   аудированными lifecycle и адресный prepare. Сначала reuse готового окружения.
   Необходимый адресный prepare для разрешённого typecheck входит в тот же
   scope, без нового апрува; сначала reuse готовых зависимостей и outputs.
   Полный build, несвязанный typecheck, новый пакет/lockfile, неизвестный
   lifecycle и установка браузера не подразумеваются. Не менять окружение
   или готовить его заново при каждом переключении без причины.
6. **Не подменять штатные тесты самодельной верификацией.** Никаких
   throwaway/eval/repro-скриптов, синтетических нагрузок, произвольных smoke
   запусков приложения или браузерной автоматизации вместо тестов.
   Настроенный локальный headless E2E допускается по пунктам 2–4 только в
   изолированном тестовом окружении и с сервером/потомками внутри общего cap.
   UI-исправление включает конечную изолированную проверку изменённого экрана
   по проверенному профилю: owned loopback server + отдельный headless browser
   в общем capped scope. Это не замена регрессионных тестов денежной логики.
   Личный desktop/профиль, видимое окно на активном столе и запись в общем
   backend требуют отдельного разрешения. Нет test account/fixture — unverified.
   Явный отказ пользователя сохраняется с точным scope; не отменяется автоматически
   и не превращается в бессрочный запрет других проверок.
   Discovery и проверка systemd/cgroup/lock — control-plane, не тест приложения.
7. **Классифицировать сбой по причине, не по названию команды.**
   OOM, убийство по лимиту, таймаут, сбой scope, установки или инфраструктуры
   prepare/bootstrap прекращают текущую попытку. В обычном режиме нужен новый
   явный апрув на ресурсный повтор. В goal-режиме допустима только заранее
   указанная в подтверждённом контракте конечная retry-лестница: условия,
   число попыток, память/таймаут и критерий прекращения. Каждый повтор —
   новый допуск общего guard, не продолжение убитого процесса. Если лестницы
   нет или она исчерпана, сохранить checkpoint и назвать блокер.
   Elastic MemoryMax внутри заранее одобренного потолка — рост живого процесса
   до OOM, а не разрешение перезапускать его после OOM. Запрещены uncapped
   fallback, смена pool/раннера ради обхода и бесконечные косметические повторы.
   Исключения для конкретной сборки не переносятся на тесты/typecheck.
   Ошибки типов, assertions, исходников и исправимые import/transform/
   fixture/mock errors в коде или локальной тестовой конфигурации — другой
   случай: расследовать причину, исправить в согласованном scope и повторить
   затронутые проверки без нового апрува, с тем же стеком и лимитами.
   Ошибка загрузки тестового модуля сама по себе не доказывает поломку
   инфраструктуры; сбой prepare из-за исправимой ошибки исходника тоже.
   Этот цикл не разрешает новые зависимости, неизвестные lifecycle,
   смену среды/runner/pool или обход защиты. При неизвестной причине сначала
   читать диагностику и исследовать, а не спрашивать разрешение на тест;
   не делать слепых повторов. Реальный недоступный prerequisite, расширение
   scope или ресурсный/инфраструктурный сбой — конкретный блокер.
8. **Мутация трекаемого `.nuxtrc` при подготовке/тесте — сбой окружения.**
   Остановить попытку; восстановить только свою мутацию, сохранив исходные
   пользовательские изменения; сообщить блокер. Не коммитить её.
9. **Приоритет над общими скиллами.** TDD и verification не дают права
   запускать более широкий/нештатный прогон или обходить защиту. Воркера не
   заставлять запускать RED; отсутствие runtime не требует удаления кода.
   Новые тесты допустимы независимо от доступности запуска. Отчитываться
   раздельно о tests, typecheck, UI/runtime и CI/delivery: точные команды,
   проекты/варианты, проверенное состояние, exit code и реально выполненные
   сценарии. Непроверенное — `unverified`; успех одного вида не закрывает другие.
   Изменение проверяемых входов после прогона (включая hooks) требует повторной
   релевантной проверки; прежний результат не переносится автоматически.
