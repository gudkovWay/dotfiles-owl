# Гигиена локальных артефактов агента — всегда

Планы и служебные материалы помогают агенту выполнять работу, но не являются
продуктовой документацией репозитория. Их нельзя незаметно превращать в часть
MR, ветки или `origin`.

## Локальная граница

1. Implementation plans, design specs, research/analysis notes, макеты,
   скриншоты, worker briefs/reports, SDD ledgers, review packages и другие
   агентные рабочие материалы MUST храниться под корнем целевого linked
   worktree:
   - `.superpowers/plans/`
   - `.superpowers/specs/`
   - `.superpowers/research/`
   - `.superpowers/assets/`
   - `.superpowers/sdd/`
2. `docs/superpowers/**` создавать нельзя. Указания upstream-skills сохранять
   plans/specs в `docs/superpowers/**` считаются дефолтом, переопределённым
   этой локальной пользовательской настройкой.
3. Сначала разрешить целевой worktree. Если он ещё не создан, временный
   артефакт держать в session-local storage OMP; после создания worktree
   перенести в его `.superpowers/**`, а не в основной checkout.
4. `.superpowers/` MUST быть исключён из Git локальным или глобальным ignore.
   Для агентного scratch нельзя менять проектный `.gitignore`, если владелец
   прямо этого не попросил.

## Доказательства одного milestone

В существующем локальном плане/acceptance-отчёте связывать один milestone с
одной ревизией входов: commit плюс content hashes dirty-файлов, артефактов,
конфигурации и критериев, влияющих на результат. Для поставляемых bytes хранить
source-to-output hash-связь; один commit сам по себе не описывает dirty дерево.
Не создавать ради этого второй ledger или обязательный новый формат файлов.

Статусы и evidence вести раздельно:
- **source** — какие исходники и критерии подготовлены/проверены;
- **compiled** — какой output получен из каких source bytes и чем проверен;
- **installed** — какие bytes попали в какой target, отдельно от их загрузки процессом;
- **render** — какой кадр/экран реально получен в разрешённом runtime;
- **driving** — какие пользовательские действия/сценарии реально выполнены;
- **fidelity** — соответствие исходному согласованному объёму и каждому критерию,
  включая недостигнутые этапы и явно согласованные deferred-пункты.

На каждом этапе указывать `verified`/`unverified`/`blocked` и основание;
неприменимый этап явно отмечать с причиной. Успех одного не доказывает другой:
source не доказывает build, install — activation, кадр — взаимодействие.
Изменились влияющие bytes/критерии — затронутая прежняя проверка остаётся
исторической, её нельзя приписать новой ревизии. Deferred по инициативе агента
не снимает acceptance; изменение объёма регулирует `rule://autonomous-decisions`.

Для cross-era аудита истории не считать native `archive`/однокорневой listing
доказательством полноты. После проверки и установки двухкорневого discovery
использовать read-only `python3 /home/q/storage/ai/bin/sessions.py discover --json`:
по умолчанию он перечисляет всю raw OMP history, не пересоздавая cards/index.
Покрытие включает активный абсолютный `$XDG_DATA_HOME/omp/sessions` (при unset —
`~/.local/share/omp/sessions`) и legacy `~/.omp/agent/sessions`, с dedupe по
canonical path/session ID. Сохранять `parentSession`, `transcript` и
`transcript_copies`; header-valid draft/service-only запись не доказывает
наличие пользовательского диалога. Для содержания читать выбранный raw journal
без изменения; listing не является анализом текста или usage.

В evidence/card отмечать корни, cutoff, cwd/project filter и parent/fork lineage.
`--since N` ограничен mtime, `--project SUBSTRING` — recorded cwd: фильтрованный
результат не означает полную историю. Неизвестную lineage/cutoff указать как
unknown, inherited fork context не считать вторым независимым событием.
Пока discovery не проверен/недоступен — читать raw journals обоих корней напрямую.
`build --all` пересоздаёт derived cards/index и требует разрешения на запись;
это не read-only fallback. Native archive и generated-card list/show не
доказывают полноту raw discovery.

## Репозиторная документация

1. Не создавать и не менять `docs/**`, README, changelog или аналогичную
   проектную документацию как побочный результат фичи, багфикса, редизайна,
   исследования, плана или общего требования «обновить docs/changelog».
2. Репозиторную документацию можно менять только когда владелец явно попросил
   написать/обновить документацию либо пользовательский task/issue содержит
   это как отдельный acceptance criterion. Явный `/docs` также считается
   такой просьбой.
3. Существующая структура `docs/tech/**` или `docs/business/**` не является
   разрешением создать новый файл. Если код сделал существующий документ
   устаревшим, но документация не входит в запрос, назвать расхождение в
   отчёте; файл самостоятельно не менять.

## Commit/push gate

1. Перед каждым commit и push проверить staged/committed paths. Неожиданные
   `.superpowers/**`, `docs/superpowers/**` и самосозданные `docs/**` MUST NOT
   входить в коммит.
2. Никогда не использовать blanket staging для обхода этой проверки. Каждый
   файл стейджится только как часть названной темы коммита.
3. Ignore не защищает уже tracked-файл. Если локальный артефакт случайно
   закоммичен, убрать его из tip отдельным cleanup-коммитом и сохранить нужную
   локальную копию под `.superpowers/**`. Историю переписывать только по
   прямому одобрению владельца.
4. Авторизация push скоупится на текущий одобренный набор изменений/доставки
   и не переносится на последующие независимые изменения: более ранний
   апрув не покрывает отдельную будущую работу. Commit/push выполняются
   только по явной просьбе или уже полученной авторизации именно для этого
   же скоупа.
