# Display fallback для разрешённой GUI-проверки

Время суток не имеет значения. Это процедура выбора доступной поверхности внутри уже разрешённого конечного GUI-сценария, не разрешение запускать приложение при read-only аудите. В OMP авторизация одного диагностически обоснованного перехода с новой попыткой задаётся `rule://no-autotests`, §6б; в другом harness сначала проверь его полномочия и resource policy.

## Диагностика до перехода

1. Сохрани исходную диагностику: команда/exit reason, точный owned PID/start-time, compositor/socket, окно, geometry/scale, exposed/visibility, состояние output и доступные сведения о frame callbacks/capture. Не снимай личный desktop ради диагностики.
2. `exposed=0` само по себе не доказывает DPMS off: проверь, что окно не спрятано самим приложением и capture обращается к правильному экземпляру. Отличай изменившуюся геометрию окна от размера последнего отрисованного буфера. Не жди неопределённо и не повторяй тот же capture вслепую.
3. Если причина — неотрисовываемая поверхность (DPMS, скрытый workspace, отсутствие пригодного output/capture), выбери изолированный виртуальный output. OOM, resource timeout/kill, сломанный guard/bootstrap и crash приложения — отдельные сбои, не доказательство проблемы экрана. Не используй display fallback для обхода границы повторов; исправимую исходниковую причину crash расследуй и исправляй по правилам harness.

## Самостоятельное развёртывание

1. Сначала используй пригодный существующий owned профиль. Иначе проверь установленные compositor/backend и поддерживаемые параметры, подготовь минимальный test config с виртуальным output в ignored `.superpowers/**` целевого worktree. Не устанавливай новые зависимости без соответствующих полномочий.
2. Нужен отдельный headless compositor, чья отрисовка не зависит от физического output. Nested Wayland-окно на погашенном родительском compositor само по себе проблему не решает. `vd-run.sh --hypr` требует parent WAYLAND_DISPLAY и не является готовой гарантией headless-режима: прочитай wrapper, выбери поддерживаемый независимый backend, не выдавай его наличие за работающий профиль.
3. Сохрани native runner, проверяемые bytes, сценарий и критерии. Подготовь отдельные writable config/profile/IPC и private bus по основному скиллу; укажи socket/instance явно. Не добавляй виртуальный монитор в live compositor, не меняй его DPMS/раскладку/фокус, не включай физические экраны и не показывай host-окно.
4. Запусти compositor, приложение и capture-потомков под общим resource guard с новым допуском, без повышения ранее разрешённых caps/runtime и обхода goal envelope. Ввод направляй только в owned поверхность. Не создавай второй runner вместо штатной проверки.
5. До действий проверь реальный owned output: ненулевая geometry, enabled/DPMS-on, scale/transform и размещение клиента. Socket ready и `ok` недостаточны. Проверь свежий кадр после известного изменения состояния/resize в том же native сценарии: правильные dimensions и ожидаемое содержимое. Старый буфер не принимать за успешный capture; не снимать assertion ради зелёного теста.
6. Выполни исходные действия и reference/result comparison там, где они входят в запрос. Software backend не доказывает GPU shader fidelity: значимые отличия backend фиксируй, непроверенные критерии оставляй unverified. Заверши только свои процессы по точному ownership и проверь teardown/live preservation.

## Конечный результат

В существующем acceptance-отчёте запиши: исходный симптом и основание перехода; старый/новый профиль и source/output revision; guard job; compositor/socket/output/geometry; свежий кадр; реально выполненные действия; непроверенные критерии; teardown и сохранность live среды.

Если независимый backend отсутствует, output не создаётся или конечный fallback не прошёл — укажи точный prerequisite/сбой. Не начинай бесконечный перебор backend и не переноси блокировку проверки на независимые source-задачи. Не требуй от владельца включить мониторы или выбрать технический конфиг, который можешь определить сам.

В OMP итоговое решение о продолжении/остановке оформляй по
`rule://autonomous-decisions`, разделы «Реализация, проверка и зависимости»
и «Основание остановки перед idle»: implementation и verification раздельно,
точные зависимые этапы и доступная независимая работа, затем `stop_result`
только при отсутствии разрешённых следующих действий. Подготовленный профиль
не равен свежему кадру; свежий кадр не равен driving/fidelity PASS.
